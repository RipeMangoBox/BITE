# 2026-05-10 日报

> 基于 2026-05-10 的 ICLR 2026 批处理、PDF 检索、暂停状态与代码变更整理。

## 今日进展

### 1. ICLR 2026 PDF 检索与批处理契约

- 已从 `_private/resmax_downloads/pdfs/ICLR_2026`、`_private/huggingface/resmax`、`_private/mineru_comparison`、`paperPDFs` 检索并去重 PDF，生成 `_private/iclr26_batch/manifests/discovered_pdfs.jsonl`。
- 检索结果包含 `9971` 个已验证去重 PDF，其中 `5348` 个带 OpenReview forum id；resmax manifest 中 `123` 条因缺少 PDF 被跳过。
- 已生成 batch `iclr26_0001` 契约，选择 `25` 篇 ICLR 2026 论文，约束为 PostgreSQL 写入、MinerU-only L2、导出后人工 Markdown review 前暂停。

### 2. Batch 0001 暂停状态

- 批处理已按用户要求暂停，runner 进程已停止；当前没有继续运行的 batch 任务。
- `_private/iclr26_batch/reports/batch_0001_progress.jsonl` 已落盘 `8` 条进度：`4` 篇 `succeeded`，`4` 篇 `needs_repair`。
- 失败主因是 `analysis_agent` 输出 malformed JSON，导致 `analysis_agent_output_missing`；Markdown export 尚未到达，因此未观察到 Markdown 写盘失败。

### 3. 耗时定位与架构判断

- 已处理样本中，`analysis_agent` 成功运行平均约 `197.6s`，失败运行平均约 `254.8s`；`writer_agent` 成功运行平均约 `46.9s`。
- 当前耗时大头是 `analysis_agent` 的长结构化输出，尤其是失败 JSON 也会消耗约 4 分钟后才进入 repair 状态。
- 将 `analysis_agent + writer_agent` 合并成单 agent 可以减少一类 agent 间 handoff/blackboard 不一致问题，但不能根本解决当前 malformed JSON：如果单 agent 仍输出大 JSON，风险仍在；如果直接输出 Markdown，则会绕开现有 DeltaCard、EvidenceUnit、GraphAssertion 等结构化入库与验收门。

### 4. Resume 支持

- 已在 `researchflow-backend/scripts/run_iclr26_batch.py` 增加 `--resume`。
- resume 行为：读取 progress JSONL，跳过已有终态结果（`succeeded`、`needs_repair`、`needs_l2_repair`、`quarantined`）的 paper，只继续未落盘进度的 paper；不改变分析链路或 agent 架构。
- 已用 `py_compile` 校验 runner 语法通过。

## 核心结论

- 当前不应把“单 agent”视为 malformed JSON 的充分解决方案；它主要减少 handoff 类型问题，不会消除长结构化输出本身的失败风险。
- 本轮只采纳并实现 resume；其他关于 JSON repair、拆分输出、timeout、两阶段处理等建议暂不推进。
- `batch_0001` 后续恢复时应使用 `--resume`，避免重复处理已落盘的 8 篇。

## 问题与思考

- 若未来改成单 agent 且仍要求结构化 DB 写入，需要重新定义 schema 边界与验收门，否则会削弱现有 PostgreSQL truth layer。
- 已暂停时未进入 export 阶段，因此“如果分析 md 无法写入磁盘则停止”的条件尚未触发，也没有可验证的 Markdown 写盘失败样本。
- 当前 progress 只记录 paper 终态；如果某篇在 L2 后、agent 中途被强停且未写入进度，resume 会重新处理该 paper，这是预期行为。
