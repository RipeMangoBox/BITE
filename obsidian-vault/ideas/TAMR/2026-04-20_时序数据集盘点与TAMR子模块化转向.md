# 时序数据集盘点与 TAMR 子模块化转向

> [!abstract] **Quick Links & TL;DR**
>
> - **结论 1**：可直接服务后续计划的时序标注数据，不止 [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) 和 [FineMotion](https://github.com/BizhuWu/FineMotion)。若按“可用于研究”的强度排序，当前主列表至少应包括：[BABEL](https://github.com/abhinanda-punnakkal/BABEL)、[TEACH](https://github.com/athn-nik/teach)、[FineMoGen / HuMMan-MoGen](https://github.com/mingyuan-zhang/FineMoGen)、[FineMotion](https://github.com/BizhuWu/FineMotion)、[HumanML3D-E](https://github.com/tjswodud/EventT2M-codes)，以及可作补充的 [Motion-X](https://github.com/IDEA-Research/Motion-X)。
> - **结论 2**：今天公开可用的方法里，没有单篇工作能完整替代 TAMR 的 `temporal-aware retrieval + localization + general temporal constraints`。但可以拆件替代：[[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]] 先顶 temporal judge，[[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]] 顶 event benchmark / data asset，[[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] 顶 coarse localization / script prior。
> - **结论 3**：如果要改策略，最稳的不是“继续把 TAMR 顶成独立方法论文”，而是把它降为 `MoProbe / MoDebug` 的方法子模块；主创新往“复杂因果+并行时序计划”迁移。但这里必须正面回应 [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]]：不能再泛泛地说“我们也做 plan layer”，而要把区别收紧到 `event/body-part/parallel-aware structured plan`。`duration prediction` 应做成子模块，`streaming 无限生成` 更适合作为第二阶段扩展。

> [!warning] 公开状态说明
> 本文里“公开可用 / 不可立即用”的判断，优先依据 2026-04-20 当天核到的官方 repo / project / model page。
> repo 存在不等于 turnkey。
> 我把判断拆成三档：
>
> 1. `代码 + 权重/模型入口`：可直接排进 MVP 候选。
> 2. `代码公开，但权重未在本次核查中确认`：可作为 secondary baseline。
> 3. `仅论文 / repo 占位 / 未核到官方实现`：不纳入当前 MVP。

## 1. 我这里把“时序标注”分成四个层级

为了避免把不同性质的数据混在一起，先把后面会反复用到的层级固定下来。


| 层级                             | 含义                          | 代表用途                                        |
| ------------------------------ | --------------------------- | ------------------------------------------- |
| `event-level`                  | 序列被拆成有序事件或动作段               | 顺序约束、multi-event generation、event benchmark |
| `interval × body-part`         | 明确某个身体部位在某个时间区间做什么          | fine-grained control、局部错误定位、并行动作            |
| `frame-level text / action`    | 每帧或极细时间粒度有文本/动作标签           | frame-level planning、streaming、局部评测         |
| `sequence of (text, duration)` | 序列由多段 `(text, duration)` 组成 | 长时序编排、composition、duration prior            |


这个分法对后文很关键，因为：

- [BABEL](https://github.com/abhinanda-punnakkal/BABEL) / [TEACH](https://github.com/athn-nik/teach) 更像 `event-level` 与 `sequence planning` 资产。
- [FineMotion](https://github.com/BizhuWu/FineMotion) / [FineMoGen](https://github.com/mingyuan-zhang/FineMoGen) 更像 `interval × body-part` 资产。
- [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) 更像 benchmark layer，不是完全独立的新 motion corpus。
- [Motion-X](https://github.com/IDEA-Research/Motion-X) 更像 `frame-level` 补充。

如果后文要写“我们已经有足够强的 temporal annotation 资源”，不能把原始 `HumanML3D / KIT-ML` 算进去。

## 3. 任务一的直接结论：你后文计划里应该怎么用这些数据

如果只服务你当前的 `MoProbe / MoDebug / TAMR pivot`，我会这样排优先级：

### A. 必须进入主工作集

1. [FineMotion](https://github.com/BizhuWu/FineMotion)
2. [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes)
3. [BABEL](https://github.com/abhinanda-punnakkal/BABEL)

原因很简单：

- [FineMotion](https://github.com/BizhuWu/FineMotion) 给你 `body part × interval`。
- [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) 给你 multi-event 与顺序诊断。
- [BABEL](https://github.com/abhinanda-punnakkal/BABEL) 给你 duration / overlap / long-form 组合的母体。

这三者组合起来，刚好覆盖你现在最关心的三类 temporal signal：

- `ordering`
- `parallel / overlap`
- `duration / long-form composition`

### B. 作为第二批补强

1. [TEACH](https://github.com/athn-nik/teach)
2. [FineMoGen / HuMMan-MoGen](https://github.com/mingyuan-zhang/FineMoGen)
3. [Motion-X](https://github.com/IDEA-Research/Motion-X)

原因：

- [TEACH](https://github.com/athn-nik/teach) 最适合把“多段 `(text, duration)` 编排”规范化。
- [FineMoGen](https://github.com/mingyuan-zhang/FineMoGen) 对 `body-part stage` 很干净，适合补 [FineMotion](https://github.com/BizhuWu/FineMotion) 的 schema 偏差。
- [Motion-X](https://github.com/IDEA-Research/Motion-X) 适合作 frame-level 补充，但不该成为你当前主 benchmark。

## 4. TAMR 还能不能被现有工作替代一部分

我先把 TAMR 想承担的功能拆开。

### 4.1 TAMR 真正有三个功能位点

1. `temporal judge / reranker`
2. `temporal localization / span proposal`
3. `general temporal representation`

如果不拆开，就会误以为“只要找到一篇时序论文，就能代替 TAMR”。实际上公开方法的成熟度非常不均衡。

### 4.2 当前公开资源的可替代性判断


| 功能位点                                | 候选工作                                                                                                                                                                             | 本次核查到的公开状态                                                                                                                                           | 能否顶当前 MVP                                    | 判断               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ---------------- |
| temporal judge / ordering rerank | [[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]] | 官方 repo + Hugging Face model | `可以` | 这是当前最稳的 temporal judge 候选，但主能力集中在 `ordering`，不覆盖完整 localization |
| event benchmark / decomposition | [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]] | 官方 repo + pretrained models + [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) 入口 | `可以` | 可直接拿来做 event benchmark、multi-event prompt 与 decomposition 资产，但它不是 retrieval judge |
| coarse localization / script prior | [[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] | 官方 repo 已核到；本次至少确认代码公开 | `部分可以` | 能顶 motion localization / script 先验，但它不是 retrieval-first temporal judge，也不是 universal temporal metric |
| zero-shot motion grounding | [[paperAnalysis/Motion_Generation/AAAI_2026/2026_ZOMG_Zero_Shot_Open_Vocabulary_Human_Motion_Grounding_Test_Time_Training|ZOMG]] | 公开 repo 已核到，但本次未把它当作 turnkey code+ckpt 资源 | `暂不纳入` | 论文思路很对口，但我今天不把它算作“可以立刻接入的替代件” |
| fine-grained retrieval | [[paperAnalysis/Motion_Generation/arXiv_2026/2026_PST_Beyond_Global_Alignment_Fine_Grained_Motion_Language_Retrieval|PST]] / [[paperAnalysis/Motion_Generation/arXiv_2026/2026_MaxSim_Fine_Grained_Motion_Retrieval_Joint_Angle_Late_Interaction|MaxSim]] | 本次未核到官方公开实现或现成权重 | `不可以` | 适合 related work，不适合当前 MVP 依赖 |
| supervision denoising for retrieval | [[paperAnalysis/Motion_Generation/arXiv_2026/2026_MoCHA_Denoising_Caption_Supervision_Motion_Text_Retrieval|MoCHA]] | 本次未核到官方 repo / ckpt | `不可以` | 可作为解释路径，不适合接当前系统 |


### 4.3 所以今天最稳的 MVP 不是“替 TAMR 找一个继任者”，而是“三件套替代”

我会把当前 MVP 的 temporal stack 写成：

1. [[paperAnalysis/Motion_Generation/ICCV_2023/2023_TMR_Text_to_Motion_Retrieval_Using_Contrastive_3D_Human_Motion_Synthesis|TMR]] + [[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]]
2. [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]] / [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes)
3. [[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] or MLLM judge

具体对应关系是：


| MVP 需求                                     | 最稳替代件                     |
| ------------------------------------------ | ------------------------- |
| `顺序敏感 judge` | [[paperAnalysis/Motion_Generation/ICCV_2023/2023_TMR_Text_to_Motion_Retrieval_Using_Contrastive_3D_Human_Motion_Synthesis|TMR]] + [[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]] |
| `event decomposition / benchmark` | [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]] + [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) |
| `coarse localization / script supervision` | [[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] |
| `更一般的时序表征 + 强 localization`                | 仍然缺，TAMR 还没有被完全替掉         |


### 4.4 对 MoProbe 的结论

MoProbe 完全可以先不等完整 TAMR。

Phase A 直接用：

- `MLLM judge`
- [[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]] ordering test
- [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) / [FineMotion](https://github.com/BizhuWu/FineMotion) / [BABEL](https://github.com/abhinanda-punnakkal/BABEL) 构造 prompt set

这样就已经能把 `ordering / partial parallel / duration conflict` 的 probing 跑起来。

### 4.5 对 MoDebug 的结论

MoDebug 的第一阶段也可以不等完整 TAMR，但只能做“粗粒度版本”。

能先做的：

- 用 [FineMotion](https://github.com/BizhuWu/FineMotion) 做 pseudo span
- 用 [[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] 或 MLLM judge 做 coarse localization
- 做 `semantic error locality` 的统计

不能宣称已经解决的：

- 高质量 span-level detector 训练
- retrieval-grade temporal localization
- ordering / omission / duration / parallel 的统一高精度 localizer

换句话说：

> `TAMR 还没有被完全替代，但已经不必再当 MVP 的前置阻塞项。`

## 5. 对 TAMR 本身的策略更新

### 5.1 结论

`TAMR` 继续当独立主线，风险已经偏高。

原因不是“问题不真”，而是：

1. [[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]] 已经占住 ordering blind spot
2. [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]] 已经占住 event abstraction + [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) benchmark
3. [[paperAnalysis/Motion_Generation/arXiv_2026/2026_PST_Beyond_Global_Alignment_Fine_Grained_Motion_Language_Retrieval|PST]] / [[paperAnalysis/Motion_Generation/arXiv_2026/2026_MaxSim_Fine_Grained_Motion_Retrieval_Joint_Angle_Late_Interaction|MaxSim]] 已经占住 fine-grained retrieval
4. [[paperAnalysis/Motion_Generation/AAAI_2026/2026_ZOMG_Zero_Shot_Open_Vocabulary_Human_Motion_Grounding_Test_Time_Training|ZOMG]] / [[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] 说明 localization / script 方向也在被不同路线覆盖

所以 standalone TAMR 现在更像“拥挤交叉区”，不是“无人区”。

### 5.2 更稳的新定位

把 TAMR 收缩成：

- `MoProbe` 的 temporal judge / temporal probe backend
- `MoDebug` 的 span proposal / localization backend

这个定位有两个好处：

1. 贡献点更真实。
2. 即使 TAMR 自己最后没有独立成文，也不会让整条路线停摆。

## 6. 任务二第二部分：其他 motion temporal tasks 现在该怎么排

我这里直接按“值得主推程度”来排。

### 6.1 方向一：复杂因果顺序 + 并行顺序的结构化生成

这是我现在最建议你主推的方向。

#### 现有工作已经做到什么

- [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]]：把复杂文本拆成 ordered events，解决 multi-event generation。
- [[paperAnalysis/Motion_Generation/AAAI_2026/2026_FineXtrol_Controllable_Motion_Generation_via_Fine_Grained_Text|FineXtrol]]：把 `body part × temporal interval` 文本控制接口做实。
- [[paperAnalysis/Motion_Generation/CVPR_2026/2026_FrankenMotion_Part_level_Human_Motion_Generation_and_Composition|FrankenMotion]]：把异步 body-part 组合提升到部位级组合生成。
- [[paperAnalysis/Motion_Generation/CVPR_2026/2026_LaMoGen_Language_to_Motion_Generation_Through_LLM_Guided_Symbolic_Inference|LaMoGen]]：已经有人把 `(身体部位, 方向, 力度, 时长)` 当作显式中间符号。
- [[paperAnalysis/Motion_Generation/NeurIPS_2025/2025_TransPhase_Deep_Compositional_Phase_Diffusion_for_Long_Motion_Sequence_Generation|TransPhase]]、[[paperAnalysis/Motion_Generation/ICCV_2025/2025_InfiniDreamer_Arbitrarily_Long_Human_Motion_Generation_via_Segment_Score_Distillation|InfiniDreamer]]：已经能做多段组合和长时序过渡。

#### 但真正还没被打透的点

问题不在“能不能拆分”，而在“拆分后能不能统一执行”。

现在大多数工作仍然停在下面这条链上：

`分解 -> 各段/各部位生成 -> 拼接/平滑/局部协调`

还缺少的是：

1. 一个统一的 `temporal plan representation`
2. 同时容纳 `causal order + parallel order + body-part independence`
3. 还能被生成器真正执行，而不只是作为 hint

这正好对上你现在的核心直觉：

> 并行顺序不是简单“同时做两件事”，而是不同 body part 在同一时间轴上承担不同任务。

这个点是真正值得继续往上顶的。

#### 我的判断

这是最值得主推的一条。

因为它把几个现有缺口串起来了：

- 需要时序计划
- 需要空间细粒度
- 需要避免简单 stitching
- 还能自然吸收 duration prediction 和 streaming 作为子问题

#### 这里必须补一条：[[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] 对这条主张有直接冲击

这是当前这篇 note 里原本写得不够重的一点。

[[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] 已经做了三件对你非常关键的事：

1. 它不是简单的 streaming 工程，而是明确提出了一个 `plan -> generate` 的两阶段范式。
2. 这个 plan 不是粗粒度句级摘要，而是 **frame-level Action Plan**，比“先有规划再执行”这句口号更具体。
3. 它证明了 plan layer 不只是理论上合理，而是能同时提升 `offline / streaming / editing / inbetweening`。

所以如果你的主线还写成：

> “我们引入一个 temporal plan layer，因此比现有方法更强”

那现在已经不安全了，因为 [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] 已经把这个一般性主张占住了。

#### 但它还没有覆盖你的真正目标

我现在更准确的判断是：

- [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] 覆盖了 `future-aware frame-level planning`
- 但没有覆盖 `event/body-part/parallel-aware structured planning`

更具体地说，它的边界至少有四条：

1. **plan 的语义形态仍偏 latent frame-level**
  - 它的 Action Plan 是逐帧文本潜码，不是可解释的 `event / body-part / causal graph / parallel group` 结构。
  - 这意味着它很强，但更像“未来感知语义蓝图”，而不是“结构化任务编排语言”。
2. **它没有正面解决并行顺序的结构表达**
  - 现有描述里没有把“不同 body part 同时执行不同任务”建成显式 plan object。
  - 它能改善多动作指令执行，但不等于已经解决你关心的 `parallel order`。
3. **它依赖 BABEL 帧级文本标签，只覆盖 HumanML3D 约 30% 序列**
  - 这意味着它已经证明 frame-level plan 很有价值，但也说明这种 supervision 目前昂贵且覆盖有限。
  - 你的路线如果继续往 `event/body-part-aware plan` 走，反而可以把 `FineMotion + BABEL + HumanML3D-E` 组合成另一种 supervision source。
4. **它的主战场是 generation stack，不是诊断 / judge / localization**
  - 所以它不会替掉 `TAMR -> MoProbe / MoDebug` 这条 backend 逻辑。

#### 因此路线需要收紧，而不是放弃

[[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] 带来的不是“这条路不能做了”，而是：

> 你不能再把自己的主张表述成“我们也做 planning”。

更安全的表述应该收紧成：

> 现有工作已经证明 frame-level future-aware planning 很重要，但对 `causal order + parallel order + body-part allocation + duration allocation` 的统一结构化表达仍然缺失；我们关注的是这一层更强、更可解释、也更适合复杂指令组合的 temporal plan。

也因此，原来这里的 `P1` 最好理解成：

- 不是泛化的 plan layer
- 而是 **ActionPlan 之后的下一层：structured compositional temporal plan**

### 6.2 方向二：直接 duration prediction

这是一个真实缺口，但不适合作为单独主线。

#### 现有工作已经做到什么

- [[paperAnalysis/Motion_Generation/ECCV_2024/2024_BAMM_Bidirectional_Autoregressive_Motion_Model|BAMM]]：做了自适应长度生成，用 EOS 预测长度。
- [[paperAnalysis/Motion_Generation/Tencent_HY/2025_HY_Motion_1_0_Scaling_Flow_Matching_Text_to_Motion|HY-Motion 1.0]]：把 `duration prediction + prompt rewrite` 作为明确用户接口。
- [[paperAnalysis/Motion_Generation/CVPR_2024/2024_FlowMDM_Seamless_Human_Motion_Composition_with_Blended_Positional_Encodings|FlowMDM]]、[[paperAnalysis/Motion_Generation/NeurIPS_2025/2025_TransPhase_Deep_Compositional_Phase_Diffusion_for_Long_Motion_Sequence_Generation|TransPhase]]、[[paperAnalysis/Motion_Generation/ICCV_2023/2023_EMS_Breaking_The_Limits_of_Text_conditioned_3D_Motion_Synthesis_with_Elaborative_Descriptions|EMS]]、[[paperAnalysis/Motion_Generation/ICCV_2025/2025_InfiniDreamer_Arbitrarily_Long_Human_Motion_Generation_via_Segment_Score_Distillation|InfiniDreamer]]：都默认多段 `(text, duration)` 已给定。
- [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]]：做 implicit event time allocation，但不是显式 duration prediction。

#### 真实缺口在哪里

真正缺的是：

1. `prompt -> duration distribution`
2. `event sequence -> per-event duration plan`
3. `body-part parallel schedule -> joint duration allocation`

也就是你说的：不是“生成到停”为止，而是提前预测一份结构化时间计划。

#### 我的判断

`duration prediction` 适合做主线里的核心子模块，但单独拿出来不够顶会。

最合理的写法是：

> 我们的方法不是只预测总时长，而是预测 `event/body-part aware temporal plan`；duration 只是这个 plan 里的一个字段。

### 6.3 方向三：streaming / 无限生成

这是高上限方向，但现在不适合当第一主线。

#### 现有工作已经做到什么

- [[paperAnalysis/Motion_Generation/ICLR_2025/2025_DART_A_Diffusion_Based_Autoregressive_Motion_Model_for_Real_Time_Text_Driven_Motion_Control|DART]]：实时在线生成，支持任意长 rollout，但更像 motion primitive control。
- [[paperAnalysis/Motion_Generation/ICCV_2025/2025_MotionStreamer_Streaming_Motion_Generation_via_Diffusion_based_Autoregressive_Model_in_Causal_Latent_Space|MotionStreamer]]：首次比较完整地把 streaming T2M 做出来。
- [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]]：已经把 future-aware plan 带进 streaming，而且这个 plan 已经不只是 heuristic，而是 frame-level planning object。
- [[paperAnalysis/Motion_Generation/arXiv_2026/2026_PRISM_Streaming_Human_Motion_Generation_with_Per_Joint_Latent_Decomposition|PRISM]]：把 streaming 质量进一步拉高，说明这条赛道本身也在快速拥挤。

#### 真实还缺什么

当前 streaming 方法多数还没有认真处理：

1. 动态新增复杂指令
2. 因果顺序与并行顺序同时更新
3. `event/body-part/parallel-aware` 上层 temporal plan 与 streaming decoder 的统一接口
4. 无限生成过程中的长期 persona / style / task consistency

#### 我的判断

这条线更适合做第二阶段。

原因不是它不重要，而是：

- 工程量太大
- 赛道已经有 [[paperAnalysis/Motion_Generation/ICLR_2025/2025_DART_A_Diffusion_Based_Autoregressive_Motion_Model_for_Real_Time_Text_Driven_Motion_Control|DART]] / [[paperAnalysis/Motion_Generation/ICCV_2025/2025_MotionStreamer_Streaming_Motion_Generation_via_Diffusion_based_Autoregressive_Model_in_Causal_Latent_Space|MotionStreamer]] / [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] / [[paperAnalysis/Motion_Generation/arXiv_2026/2026_PRISM_Streaming_Human_Motion_Generation_with_Per_Joint_Latent_Decomposition|PRISM]]
- 特别是 [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] 已经把“planning improves streaming”这条一般论点做实了；如果没有一个更强、更结构化的上层 temporal plan，直接冲 streaming 很容易变成“跟现有方法比架构工程”

## 7. 新的主线排序

### 我会把接下来半年到一年的主线压成下面这个顺序


| 优先级  | 方向                                        | 定位                       |
| ---- | ----------------------------------------- | ------------------------ |
| `P1` | ActionPlan 之后的结构化 temporal plan：复杂因果+并行顺序+body-part allocation | 主论文主线 |
| `P2` | duration prediction / duration allocation | P1 的子模块                  |
| `P3` | TAMR-style temporal judge / localization  | MoProbe / MoDebug 的后端子模块 |
| `P4` | streaming / unbounded generation          | P1 证明后再接入的 phase-2       |


## 8. 一个可执行的最小策略

如果今天就收敛成 MVP，我会这样切：

### Phase A：先把现有公开资产接起来

1. [[paperAnalysis/Motion_Generation/ECCV_2024/2024_ChroAccRet_Chronologically_Accurate_Retrieval_for_Temporal_Grounding_of_Motion_Language_Models|ChroAccRet]] 做 ordering judge
2. [[paperAnalysis/Motion_Generation/ICLR_2026/2026_Event_T2M_Event_Level_Conditioning_Complex_Text_to_Motion_Synthesis|Event-T2M]] / [HumanML3D-E](https://github.com/tjswodud/EventT2M-codes) 做 multi-event benchmark
3. [FineMotion](https://github.com/BizhuWu/FineMotion) 做 `body part × interval` 数据资产
4. [BABEL](https://github.com/abhinanda-punnakkal/BABEL) / [TEACH](https://github.com/athn-nik/teach) 做 duration 与 long-form planning 资产
5. [[paperAnalysis/Motion_Generation/CVPR_2025/2025_MG_MotionLLM_A_Unified_Framework_for_Motion_Comprehension_and_Generation_across_Multiple_Granularities|MG-MotionLLM]] + MLLM judge 做 coarse localization / script baseline

### Phase B：把主创新放在 plan layer

目标不是再造一个 retrieval 模型，也不是重复一个“frame-level Action Plan”，而是定义一个更强的中间层，例如：

`text -> temporal plan -> motion`

其中 temporal plan 至少显式包含：

- `events`
- `causal order`
- `parallel groups`
- `body-part allocation`
- `duration allocation`

### Phase C：再往 streaming 接

等 Phase B 证明 plan 真的有用，再考虑：

- 用 [[paperAnalysis/Motion_Generation/CVPR_2026/2026_ActionPlan_Future_Aware_Streaming_Motion_Synthesis_via_Frame_Level_Action_Planning|ActionPlan]] / [[paperAnalysis/Motion_Generation/arXiv_2026/2026_PRISM_Streaming_Human_Motion_Generation_with_Per_Joint_Latent_Decomposition|PRISM]] 风格 decoder 接 plan
- 或把 plan 先用于 offline generation，再延展到 streaming

## 9. 这份笔记最重要的一句收束

现在最稳的路线不是：

> “继续证明 TAMR 本身还有没有论文空间”

而是：

> “先承认公开生态已经能替 TAMR 顶掉一部分功能，让 TAMR 退成 MoProbe / MoDebug 的 temporal backend；把主创新资源投向一个更大的缺口：复杂因果+并行顺序下的结构化 temporal plan。”
