> [!tip] 核心洞察

## 概要

本文针对代码优化中LLM的两个核心瓶颈——**优化视角局限**与**正确性保障缺失**——提出了系统性的解决方案。现有方法采用“用户导向视角”，即从单个程序员的提交历史中提取顺序优化对，这导致模型仅能学习局部增量改进，难以实现全局算法创新；同时，优化后的代码常因“优化税”而牺牲正确性。

**核心方法**包含两个协同组件：

1. **问题导向视角（Problem-Oriented Perspective）**：将同一编程问题的所有用户提交按运行时间排序，构建跨用户的优化轨迹。这一视角从根本上改变了优化对的构建方式，使得优化对数量从用户导向的 $\frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} \sum_{u=1}^{\mathcal{U}} C_{n_u}^2$ 扩展为 $\frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} C_{\sum_{u=1}^{u} n_u}^2$，显著缓解了数据稀缺问题。图编辑距离（GED）分析和人类标注均表明，问题导向优化对中全局算法优化的比例远高于用户导向对（Figure 2, Figure 4）。

2. **锚点验证框架（Anchor Verification Framework）**：利用功能正确但效率低下的“慢代码”作为黄金标准锚点，通过三阶段流程（测试输入生成→验证测试用例构建→迭代精炼）生成精确的验证测试用例，从而在优化过程中嵌入可执行的正确定性检查。

**主要实验结果**（基于C++测试集，gem5模拟器，QWEN2.5-CODER 32B模型）：

- **问题导向视角**将优化率从31.24%提升至58.90%（+27.66%），加速比从2.95×提升至5.22×（+2.27×），正确性从46.52%提升至61.55%（+15.03%）（Table 1）。
- **锚点验证框架**（基于DEEPSEEK-V3）进一步将优化率推至71.06%（+12.16%），加速比至6.08×（+0.86×），正确性至74.54%（+12.99%）（Table 2）。
- 消融实验表明，即使仅使用30%的问题导向优化对，模型在优化率和加速比上仍超越完整的用户导向数据集（Figure 5）；高GED（全局变更）的优化对反而增强学习效果（Appendix N, Table 12）。

**方法定位**：本文的工作处于代码生成与程序优化交叉领域，通过数据构建视角的创新和验证机制的引入，使LLM能够在保持较高正确性的前提下实现更激进的性能优化。当前局限包括：约一半的失败属于“编译通过但语义错误”类别，表明LLM在理解高级程序意图方面仍存在盲点；锚点验证框架依赖慢代码的可执行性，对执行时间不可容忍的场景适用性受限。

代码优化是提升程序执行效率的核心手段，但现有基于大语言模型（LLM）的代码优化方法面临两个根本性瓶颈。第一，**优化视角的局限性**：当前主流方法采用“用户导向视角”（User-Oriented Perspective），即从单个程序员的迭代提交中提取顺序优化对（PIE数据集）。这种视角受限于单一程序员的思维模式，优化对仅反映局部增量改进（如变量重命名、循环微调），缺乏全局算法创新。第二，**正确性与性能的权衡**：优化过程存在“优化税”（optimization tax）——优化后的代码可能牺牲正确性。现有方法缺乏有效的验证机制，导致优化率与正确性难以兼得。

本文的核心动机是回答：能否通过改变优化对的构建视角，让LLM学习到更本质的算法级优化模式？同时，能否利用慢代码本身作为可信锚点，构建精确的验证测试用例来保障优化代码的正确性？

**问题导向视角的提出**：本文提出将优化对的构建从“用户导向”转变为“问题导向”。具体而言，对于同一编程问题，将所有用户的合法提交按运行时间排序，构建跨用户的优化轨迹（PCO数据集）。这一简单转变带来了三个关键变化：（1）**数据规模优势**：问题导向视角下优化对数量为 $\frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} C_{\sum_{u=1}^{u} n_u}^2$，远大于用户导向的 $\frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} \sum_{u=1}^{\mathcal{U}} C_{n_u}^2$，有效缓解数据稀缺问题（Section 2.1）。（2）**全局算法变更**：图编辑距离（GED）分析表明，问题导向优化对的GED显著高于用户导向对，意味着前者更可能涉及全局算法调整和主要结构修改（Figure 2）。人类分析进一步确认，PCO中全局算法优化的比例远高于PIE（Figure 4）。（3）**性能飞跃**：在QWEN2.5-CODER 32B上，问题导向视角将优化率从31.24%提升至58.90%，加速比从2.95×提升至5.22×（Table 1）。即使仅使用30%的PCO优化对，LLM的优化率和加速比仍超越完整的PIE数据集（Figure 5），证明增益主要来自视角本身而非数据规模。

**锚点验证框架的动机**：尽管问题导向视角大幅提升了优化能力，但正确性仅为61.55%，仍有约40%的优化代码存在语义错误。现有验证方法（如Self Debugging）依赖LLM生成测试用例和预期输出，但LLM自身可能产生错误的预期输出，导致验证失效。本文的核心洞察是：慢代码虽然效率低，但功能正确，可以作为“黄金标准锚点”。锚点验证框架的三阶段设计（Figure 6）正是基于这一洞察——利用LLM解释慢代码功能生成测试输入，然后通过执行慢代码获得精确输出，构建验证测试用例，最后进行迭代精炼。这一机制将正确性从61.55%提升至74.54%，优化率提升至71.06%，加速比提升至6.08×（Table 2）。

**与现有方法的区别**：本文的方法与直接测试生成和Self Debugging有本质不同。直接测试生成依赖LLM同时生成输入和预期输出，存在双重不确定性；Self Debugging通过双向执行过滤来验证，但缺乏精确的预期输出。锚点验证框架通过执行慢代码获得确定性的预期输出，从根本上解决了验证信号的可靠性问题。消融实验表明，锚点验证在Python版本上同样优于这些对比方法（Appendix J, Table 9）。

**需要人工验证的点**：关于问题导向视角的泛化能力——实验仅针对C++和Python语言，对其他编程语言（如Java、Rust）的适用性尚未验证。此外，锚点验证框架依赖慢代码的可执行性，对于执行时间不可容忍的慢代码场景，其适用性受限。这些局限性在论文的开放问题部分有明确讨论。

## 核心方法与创新机理

该工作的核心创新在于将代码优化的切入点从“用户视角”转向“问题视角”，并配套设计了一个基于慢代码的“锚点验证”框架，从根本上解决了现有方法优化率低、正确性差的问题。

### 创新一：从用户导向到问题导向的视角转换

现有方法（如PIE数据集）从单个程序员的提交历史中提取优化对（慢代码→快代码）。这种**用户导向视角**天然受限：单个程序员的知识边界和思维模式导致优化仅停留在局部增量改进（如变量重命名、循环微调），难以触及全局算法创新。

本文提出的**问题导向视角**颠覆了这一构建方式。它将同一编程问题的所有用户提交按运行时间排序，构建跨用户的优化轨迹（见Figure 1）。这一转变带来了两个核心优势：

1. **引入全局算法变更**：问题导向优化对的图编辑距离（GED）显著高于用户导向对（Figure 2），表明这些优化涉及算法调整和主要结构修改。人类分析进一步证实，问题导向对中“全局算法优化”的比例远高于用户导向对（Figure 4）。
2. **缓解数据稀疏**：问题导向视角下优化对的数量计算公式为 $\frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} C_{\sum_{u=1}^{u} n_u}^2$，相比用户导向的 $\frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} \sum_{u=1}^{\mathcal{U}} C_{n_u}^2$，通过跨用户组合显著增加了数据量。

该创新的效果在实验中得到了直接验证：在QWEN2.5-CODER 32B模型上，问题导向视角将优化率从31.24%提升至58.90%，加速比从2.95×提升至5.22×（Table 1）。消融实验进一步证明，即使仅使用30%的问题导向优化对，LLM在优化率和加速比上仍超越完整的用户导向数据集（Figure 5）。附录H中的PCO-Random实验（随机选择问题导向对）在所有指标上显著优于PIE，确证了问题导向视角本身是主要增益来源，而非选择偏差。

### 创新二：锚点验证框架

代码优化的核心矛盾在于“优化税”（optimization tax）：优化后的代码虽然更快，但可能牺牲正确性。本文提出的**锚点验证框架**（Figure 6）通过一个三阶段流程，利用慢代码本身作为“黄金标准锚点”来生成精确的验证测试用例，从而在提升优化率的同时显著提高正确性。

**阶段1：测试输入生成**——LLM解释慢代码的功能，生成覆盖边界情况的测试输入。
**阶段2：验证测试用例构建**——将测试输入通过慢代码编译执行，获得精确输出，形成完整的验证测试用例。这里的核心洞察是：慢代码虽然效率低，但功能是正确的，因此其输出可以作为“锚点”来验证优化代码的正确性。
**阶段3：迭代精炼**——利用验证测试用例对优化代码进行编译执行和正确性检查，迭代修正错误。

该框架的关键创新在于：它不依赖LLM自行生成正确的测试用例（如Self Debugging方法），而是通过慢代码的实际执行获得**绝对正确的输出**，从而避免了LLM在测试生成中的幻觉问题。

实验结果表明，锚点验证框架在DEEPSEEK-V3上进一步将优化率从58.90%提升至71.06%，加速比从5.22×提升至6.08×，正确性从61.55%提升至74.54%（Table 2）。增加迭代次数可进一步提升性能：5次迭代后正确性达79.24%，优化率达78.43%，加速比达6.37×（Table 4）。在Python版本上的实验同样验证了该框架优于Self Debugging和Direct Test Generation方法（Appendix J, Table 9）。

**两个创新的协同效应**：问题导向视角提供了更丰富、更全局的优化模式学习素材，解决了“优化什么”的问题；锚点验证框架则确保了这些优化在实践中的正确性，解决了“如何安全优化”的问题。两者结合使得代码优化从“局部增量改进”跃迁为“全局算法创新+正确性保障”的系统性方案。

本文提出的代码优化框架由两个核心模块串联而成：**问题导向优化对构建**与**锚点验证框架**，二者分别解决数据源质量与优化后代码正确性保障这两个瓶颈。

### 模块一：问题导向优化对构建（数据层）

该模块的核心操作是将同一编程问题的所有用户提交，按运行时间排序后映射到同一优化轨迹上，从而构建跨用户的优化对（即 `PCO` 数据集）。这与传统用户导向视角（`PIE`）截然不同——后者仅从单个用户的迭代提交中提取顺序优化对，受限于单一程序员思维模式，优化模式多为局部增量修改。具体而言，对于问题 `P`，若所有用户的有效提交数为 `n_u`，则问题导向视角下优化对数量为 `# optimization pairs of problem oriented = (1/2) · Σ C_{∑n_u}^2`，而用户导向视角为 `# optimization pairs of user oriented = (1/2) · Σ Σ C_{n_u}^2`。问题导向视角通过跨用户整合，不仅缓解了数据稀疏性，更引入了全局算法变更——图编辑距离（GED）分析（Figure 2）和人类分析（Figure 4）一致表明，PCO 中的优化对具有显著更高的 GED，且全局算法优化占比远高于 PIE。该模块的输出作为监督微调（SFT）的训练数据，使 Code LLM 学习到从局部编辑到算法级重构的多样化优化模式。

### 模块二：锚点验证框架（正确性保障层）

该框架是一个三阶段迭代精炼流程（Figure 6），旨在消除“优化税”——即优化代码可能牺牲正确性的问题。其核心洞察是利用功能正确但效率低的慢代码作为**黄金标准锚点**，通过执行生成精确测试用例，而非依赖模型自行合成或猜测输出。

- **阶段1：测试输入生成**：LLM 被提示解释慢代码的功能，并生成覆盖边界情况的测试输入。此阶段不要求输出正确性，仅生成输入集合。
- **阶段2：验证测试用例构建**：将阶段1生成的测试输入送入慢代码进行编译和执行，获得精确输出，从而形成完整的、可执行的验证测试用例集。这一步骤的关键在于，输出由真实执行产生，而非模型生成，因此不存在幻觉或语义偏差。
- **阶段3：迭代精炼**：利用验证测试用例集对优化代码进行编译执行和正确性检查。若优化代码未能通过所有测试用例，则将执行反馈（包括编译错误、运行时错误或输出不匹配）回传给 LLM，要求其修正代码。该过程可重复迭代（实验中最多5次），直至所有测试用例通过或达到最大迭代次数。

### 整体输入输出流

1. **输入**：同一编程问题的多用户提交代码集合（包含运行时间标注）。
2. **问题导向优化对构建**：输出 `PCO` 数据集（与 PIE 等量优化对，78K 对，按每个问题最高加速比选择）。
3. **监督微调**：在 PCO 上对 Code LLM（如 QWEN2.5-CODER 32B）进行 SFT，输出具备问题导向优化能力的基线模型。
4. **锚点验证框架**：以基线模型的优化输出为输入，结合原始慢代码，输出经过正确性验证的最终优化代码。该框架可集成不同 LLM（如 GPT-4o、DEEPSEEK-V3）作为精炼引擎。

### 模块间因果关系

问题导向视角通过提升优化对的结构多样性（高 GED、全局算法变更），使 LLM 学会更激进的优化模式，从而将优化率从 31.24% 提升至 58.90%，加速比从 2.95× 提升至 5.22×（Table 1）。然而，这种激进优化也带来了正确性下降的风险（61.55% 的正确性）。锚点验证框架通过慢代码锚点生成的精确测试用例进行迭代精炼，在保持高优化率的基础上，进一步将优化率提升至 71.06%，加速比至 6.08×，同时将正确性提升至 74.54%（Table 2）。两个模块形成互补：前者扩大优化空间，后者收缩正确性边界，共同实现“更高性能 + 更高正确性”的 Pareto 改进。

**证据强度说明**：所有关键性能数据均来自 Table 1、Table 2 和 Section 1 的明确声明，置信度为 1.0。模块间因果关系（问题导向视角提升优化率 → 锚点验证框架弥补正确性）由实验设计（先 SFT 再精炼）和消融实验（Figure 5 显示 PCO 数据量减少时性能下降）支持，属于因果推断而非直接测量，需注意这一逻辑链条的强度依赖于实验设计的内部有效性。

### 优化对构建视角的数学形式化

论文核心创新在于将代码优化对的构建从“用户导向”转变为“问题导向”。两种视角下的优化对数量可分别用组合数公式量化：

*   **用户导向优化对数量**：$\#\text{ optimization pairs of user oriented} = \frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} \sum_{u=1}^{\mathcal{U}} C_{n_u}^2$，其中 $\mathcal{P}$ 为问题总数，$\mathcal{U}$ 为用户总数，$n_u$ 为用户 $u$ 对问题 $p$ 的有效提交数。该公式从每个用户的个人提交轨迹中提取顺序优化对，反映了单一程序员视角下的增量改进。
*   **问题导向优化对数量**：$\#\text{ optimization pairs of problem oriented} = \frac{1}{2} \cdot \sum_{p=1}^{\mathcal{P}} C_{\sum_{u=1}^{u} n_u}^2$，其中所有用户对同一问题的有效提交被合并排序，构建跨用户的优化轨迹。该视角不仅缓解了数据稀疏性（用户导向视角下单一用户提交数有限），更重要的是引入了全局算法变更的可能性。

### 加速比与性能度量

优化性能的核心度量是加速比（SPEEDUP），定义为：$SPEEDUP(O, N) = \frac{o}{n}$，其中 $o$ 为旧代码（慢代码）运行时间，$n$ 为新代码（优化代码）运行时间。该指标仅在代码通过正确性检查时计入统计，体现了“优化税”（optimization tax）问题——即优化可能牺牲正确性。

### 锚点验证框架的三阶段流程

锚点验证框架是确保优化正确性的核心机制，包含三个阶段：

1.  **测试输入生成（Stage 1）**：LLM 被提示解释“慢代码”的功能，并生成覆盖边界情况的测试输入集。
2.  **验证测试用例构建（Stage 2）**：将第一阶段生成的测试输入通过“慢代码”进行编译和实际执行，获得精确输出。此处“慢代码”作为黄金标准锚点（gold-standard verification anchor），其功能正确性（尽管效率低）保证了测试输出的可靠性。
3.  **迭代精炼（Stage 3）**：利用验证后的测试用例集，对优化代码进行编译执行和正确性检查，通过执行反馈迭代修正错误。

### 算法复杂度示例

论文通过具体案例展示了问题导向视角下全局算法变更带来的复杂度降低（Figure 18）：

*   **递归DP解决方案（图18a）**：查询时间复杂度为 $\mathcal{O}(N^2)$。
*   **二分搜索解决方案（图18b）**：查询时间复杂度为 $\mathcal{O}(N \cdot \log(N))$。
*   **二维前缀和解决方案（图18c）**：查询时间复杂度为 $\mathcal{O}(1)$。

这一从 $\mathcal{O}(N^2)$ 到 $\mathcal{O}(1)$ 的跃迁体现了问题导向视角能够引入根本性的算法范式转换，而非局部增量改进。

### 错误模式与修正条件

论文识别了两种典型的优化错误模式（Figure 21-22）：

*   **状态转移不完整**：代码未正确处理跳跃限制K，仅考虑相邻位置代价而忽略更大跳跃范围。修正方案是使用双循环动态更新每个位置的最小代价。
*   **循环终止条件错误**：错误代码使用 $mx < n - 1$ 提前终止循环，而正确条件应为 $mx < n$，确保仅当最大值小于n时才停止循环。

这些错误模式揭示了LLM在理解高级程序意图方面的盲点，也是锚点验证框架需要迭代精炼的根本原因。

## 实验与关键发现

### 主结果：问题导向视角 vs. 用户导向视角

核心实验比较了在相同规模的优化对数据集上，采用问题导向视角（PCO）与用户导向视角（PIE）微调代码大语言模型（Code LLM）的性能差异。实验在C++代码上使用gem5 CPU模拟器进行，所有模型采用BEST@1和BEST@8策略评估。

**Table 1** 展示了关键结果。以 QWEN2.5-CODER 32B 为例，在BEST@1下，PCO微调模型将优化率（%OPT）从PIE的31.24%提升至58.90%（+27.66%），加速比（SPEEDUP）从2.95×提升至5.22×（+2.27×），正确性（CORRECT）从46.52%提升至61.55%（+15.03%）。这一增益在BEST@8下同样显著，且在不同模型（如GPT-4o、DEEPSEEK-V3）上一致复现。该结果表明，**问题导向视角是性能提升的主要瓶颈**，它通过整合同一问题的多个程序员解决方案，使模型学习到用户导向视角难以触及的全局算法创新。

### 消融实验与机制分析

**数据效率与视角主导性（Figure 5 & Table 6）**：Figure 5 显示，即使仅使用30%的PCO优化对，LLM在%OPT和SPEEDUP上已超越使用完整PIE数据集的模型。这表明PCO的数据效率远高于PIE。为进一步排除“选择偏向”（即PCO倾向于选择加速比更高的对）的干扰，附录H的Table 6对比了PCO-Random（从PCO池中随机选择对）与PIE。PCO-Random在所有指标上显著优于PIE（如%OPT: 49.55% vs. 26.96%），证明**问题导向视角本身是增益的主要来源**，而选择偏向仅起次要作用。

**优化对结构差异的影响（Table 12）**：Figure 2 显示，PCO优化对的图编辑距离（GED）显著高于PIE，表明前者涉及更全局的结构变更。Table 12 的消融实验进一步验证了这一点：仅用高GED对训练的模型，在所有指标上优于低GED模型（%OPT: +9.74%，SPEEDUP: +0.73×）和随机子集模型（%OPT: +5.91%，SPEEDUP: +0.373×）。这证实**高GED的全局算法变更不仅没有阻碍学习，反而增强了模型对核心优化模式的掌握**。

### 锚点验证框架结果

**主结果（Table 2）**：在PCO微调模型输出的基础上应用锚点验证框架，以DEEPSEEK-V3为验证器，BEST@1下%OPT从58.90%提升至71.06%（+12.16%），SPEEDUP从5.22×提升至6.08×（+0.86×），CORRECT从61.55%提升至74.54%（+12.99%）。该框架在所有模型上一致优于无精炼的基线，也优于Self Debugging和Direct Test Generation两种对比方法。

### Python版本与硬件验证

**跨语言泛化（Table 8 & Table 9）**：在Python版本上，PCO微调的优势依然显著（如QWEN2.5-CODER 32B: %OPT 80.05% vs. PIE 53.50%）。锚点验证框架在Python上同样优于Self Debugging和Direct Test Generation（Table 9），表明该方法具有跨语言泛化潜力。但需注意，该泛化性目前仅对C++和Python得到验证。

**物理硬件验证（Table 13）**：为排除模拟器偏差，在物理硬件上验证了10个优化案例。gem5模拟的加速比与物理硬件加速比呈强正相关（Pearson相关系数0.89），但gem5系统性地高估了加速比（平均6.9× vs. 硬件6.1×，相对误差-11.6%）。这表明模拟器结果可靠，但绝对数值需谨慎解读。

### 失败模式分析

**Table 7** 的失败模式分析揭示了LLM在代码优化中的主要瓶颈。约一半的失败属于“编译通过但语义错误”类别，表明**当前LLM在理解高级程序意图方面存在系统性盲点**。例如，Figure 21 的案例中，模型未能正确处理跳跃限制K的状态转移逻辑，仅考虑了相邻位置的成本；Figure 22 的案例中，模型使用了错误的循环终止条件 `mx < n - 1` 而非正确的 `mx < n`。这些失败模式表明，尽管锚点验证框架显著提升了正确性，但实现“零正确性损失优化”仍是一个开放挑战。

## 定位与知识库关联

该工作定位在“代码优化的自动化”这一长期挑战中，核心创新在于将优化视角从**用户导向**（PIE）切换为**问题导向**（PCO），并辅以**锚点验证框架**来解决伴随而来的正确性风险。其方法谱系与现有工作的关系、适用边界及开放问题如下。

### 与基线/后续工作的关系

1.  **超越用户导向的局部增量改进**：现有工作（如PIE数据集）从同一用户的迭代提交中提取优化对，受限于单一程序员的思维模式，优化类型多为局部微调（如变量重命名、循环展开），难以触及全局算法创新。本文通过分析同一问题的所有用户提交，按运行时间排序构建跨用户优化轨迹，从根本上改变了训练数据的分布。**决定性证据**是：问题导向优化对的图编辑距离（GED）显著高于用户导向对（Figure 2），且人类分析表明前者中全局算法优化的比例远高于后者（Figure 4）。这直接导致了优化率从31.24%提升至58.90%，加速比从2.95×提升至5.22×（Table 1, QWEN2.5-CODER 32B）。

2.  **锚点验证框架 vs. 现有正确性保障机制**：代码优化存在“优化税”（optimization tax），即优化可能牺牲正确性。现有方法如Self Debugging和Direct Test Generation依赖模型自身生成测试用例或进行自我调试，缺乏可靠的金标准。本文的锚点验证框架利用**慢代码**（功能正确但效率低）作为可信锚点：先生成测试输入，再通过慢代码的实际执行获得精确输出，构建验证测试用例，进行迭代精炼。**关键优势**在于：锚点是实际执行结果，避免了模型生成测试用例时的幻觉。实验表明，该框架在DEEPSEEK-V3上将正确性从61.55%提升至74.54%，优化率从58.90%提升至71.06%（Table 2），且5次迭代后正确性可达79.24%（Table 4）。在Python版本上，该框架同样优于Self Debugging和Direct Test Generation（Appendix J, Table 9）。

3.  **消融实验确认核心增益来源**：通过对比PCO-Random（随机选择问题导向对）与PIE，证明了问题导向视角本身是主要增益来源，而非选择高加速比对带来的偏差（Appendix H, Table 6）。进一步，高GED的优化对（代表全局算法变更）反而增强学习效果：仅用高GED对训练的模型在所有指标上优于低GED模型和随机子集模型（Appendix N, Table 12），表明学习根本性的算法变换比学习增量改进更有价值。

### 适用边界与局限性

1.  **依赖慢代码的可执行性**：锚点验证框架的核心是使用慢代码作为执行锚点。对于执行时间不可容忍（如需要数小时或数天）的慢代码，该框架的适用性受限。论文自身也承认这一点，并作为开放问题提出。

2.  **语言泛化能力有限**：实验主要针对C++和Python。虽然Python版本上取得了类似结论（Table 8, 9），但对Java、Rust等语言的泛化能力尚未验证。

3.  **语义错误的根本原因未解**：当前LLM在理解高级程序意图方面仍存在盲点。失败模式分析（Table 7）显示，约一半的失败属于“编译通过但语义错误”类别。论文指出了这一现象，但未深入揭示LLM的具体盲点。

### 开放问题

1.  **扩展到系统级和大规模代码库**：当前方法聚焦于单个函数的优化，如何将其扩展到系统级挑战（如跨模块优化、内存布局优化）和大型代码库（如百万行级）是核心开放问题。

2.  **实现“零正确性损失优化”**：尽管锚点验证大幅提升了正确性，但仍有约25%的优化代码存在错误。如何确保代码优化的完全正确性，是一个多方面的复杂挑战。

3.  **适应不可容忍的执行场景**：对于执行时间极长的慢代码，如何设计替代的验证机制（如静态分析、形式化验证）是未来方向。

4.  **迁移到未见问题类型**：从PCO学到的编辑模式（如将嵌套循环重写为前缀和预处理）能否有效迁移到未见的问题类型？这需要进一步验证。

5.  **BEST@k策略下的最优平衡**：在BEST@k策略下，优化率（%OPT）与正确性（CORRECT）之间存在权衡。如何找到最优平衡点，以及如何设计更智能的选择策略，是值得探索的方向。
