## 概述

随着大语言模型（LLM）在智能体系统中扮演日益核心的角色，其工作流规划与工具编排能力成为决定系统可靠性的关键瓶颈。然而，现有评测基准普遍缺乏对LLM在真实多领域约束下进行结构化规划与工具执行能力的系统评估，尤其无法有效解耦规划能力与执行能力，导致难以定位模型失效的根源。

针对这一缺口，本文提出**OrchestrationBench**——一个双语、多领域的LLM驱动智能体规划与工具使用评测基准。其核心设计理念是将编排任务显式分解为**工作流规划**与**约束感知工具执行**两个独立可评估的维度：工作流规划以有向无环图（DAG）形式建模，通过图编辑距离（GED）量化评估；工具执行则覆盖工具选择、参数提取与约束验证，并引入呼叫/拒识分类以区分执行失败与合理拒绝。

核心发现具有明确的因果指向：**工具执行性能在不同模型间相对一致，而规划能力差异巨大**。例如，英文数据集上最优模型的规划得分（1-GED）可达0.850，而最弱模型仅0.057，差距达0.793。这一现象揭示了当前LLM在结构化规划层面存在显著分化，凸显了对规划能力进行独立、精细化评估的迫切需求。

在方法定位上，OrchestrationBench区别于现有基准（如BFCL、τ-bench等）的关键在于其同时覆盖多智能体协作、函数调用、工具调用、多轮对话、结构化规划与多语言六个维度（Table 1），并采用纯人工标注构建了涵盖17个领域、近100个工具的评测数据集，包含约束验证与动态修订等复杂场景。评估体系引入三阶段LLM裁判团进行语义正确性仲裁，以缓解传统精确匹配的局限性。

主要结果方面，在英文数据集上，Claude-sonnet-4与开源模型Qwen3-235B-A22B以0.842的总分并列最佳，展示了开源模型的竞争力；韩文数据集上Gemini-2.5-pro-preview以0.839领先。相关性分析进一步验证了评测框架的合理性：规划得分与函数调用得分高度相关（英文ρ=0.9215），但呼叫/拒识分类与规划得分的相关性仅为中等（英文ρ=0.5830），说明这三者捕捉了不同维度的能力信号，联合评估具有互补价值。

## 背景与动机

### 智能体编排的现实需求

大语言模型（LLM）正从单一对话代理向多智能体协作系统演进。在真实服务场景中，用户请求往往跨越多个领域——例如同时预订演唱会门票、餐厅和日程安排——这要求一个主控LLM将复杂目标分解为结构化工作流，并动态协调多个子LLM执行工具调用。这种“LLM到LLM”的分层编排范式（OrchestrationBench将其形式化为Figure 1所示的架构）已成为构建可靠智能体系统的核心挑战。

### 现有评测基准的结构性缺口

当前评测体系存在三个关键盲区：

1. **规划与执行耦合评估**。多数基准将工作流规划与工具调用混为一体评分，无法区分“规划错误”与“执行错误”。例如，一个模型可能正确选择了工具但规划了错误的依赖顺序，现有指标难以归因。

2. **领域与约束覆盖不足**。如Table 1所示，主流基准（如ToolBench、BFCL、τ-bench等）在多智能体协作、函数调用、多轮对话、规划评估、多语言支持等维度上均存在缺失。仅有OrchestrationBench同时覆盖全部六个能力维度。

3. **缺乏结构化规划度量**。现有工作流评估多依赖端到端任务成功率，缺少对DAG结构本身（节点选择、边依赖、执行状态）的细粒度度量，导致规划能力的诊断性评估几乎空白。

### 核心瓶颈与本文动机

该工作的核心洞察可归纳为：**工具执行性能在不同模型间相对一致，而规划能力差异巨大**。实验表明，模型间的函数调用得分差异远小于规划得分差异——例如EXAONE-4.0-32B的规划得分仅0.057，而最佳模型可达0.850。这一“规划-执行鸿沟”揭示了当前LLM在结构化工作流编排上的根本性短板，也凸显了将规划能力从工具使用能力中解耦评估的迫切需求。

基于此，本文提出**OrchestrationBench**，一个双语、多领域的评测基准，通过图编辑距离（GED）等结构化指标将规划与工具执行评估分离，并提供覆盖17个领域、近100个工具的纯人工标注数据集，系统度量LLM在约束感知和动态修订场景下的编排能力。

## 核心创新

OrchestrationBench 的核心创新在于首次将 LLM 驱动的智能体编排能力**系统性地解耦为工作流规划与约束感知工具执行两个独立维度**，并分别设计了精细化的评估协议。这一设计直接回应了现有评测基准的根本瓶颈：缺乏对真实多领域约束下规划与执行能力的区分性评估。

### 规划-执行解耦评估

现有基准（如 BFCL、τ-bench）通常将工具调用正确性作为单一指标，无法区分模型是在“规划阶段”出错还是在“执行阶段”出错。OrchestrationBench 通过以下机制实现解耦：

- **工作流规划**：将编排形式化为有向无环图（DAG）的构建任务，主 LLM 需将用户请求分解为具有依赖关系、执行状态和子 LLM 指派的步骤化工作流。评估采用**图编辑距离（GED）**，归一化后以 1-GED 报告，其中工作流选择错误权重 0.8，状态错误权重 0.2。
- **工具执行**：进一步分解为两个序贯评估标准——**呼叫/拒识分类准确率**（判断是否需要调用工具及是否触发约束违规）和**函数调用 F1**（涵盖工具选择 F1、参数键 F1、参数值 F1）。语义正确性由三个 LLM 裁判（GPT-4.1、Claude Sonnet 4、Gemini 2.5 Flash）集成仲裁，Cohen’s Kappa 为 0.63。

这一解耦设计揭示了一个关键发现：**工具执行性能在不同模型间相对一致，而规划能力差异巨大**——例如 EXAONE-4.0-32B 的规划得分仅为 0.057，而最佳模型可达 0.850。这凸显了结构化规划评估的迫切需求，也为后续训练策略（如针对规划能力的强化学习）提供了明确的优化方向。

### 纯人工标注的多领域双语数据集

与多数依赖 LLM 合成数据的基准不同，OrchestrationBench 的数据集**完全由训练有素的标注者按照详细构建指南人工创建**，涵盖 17 个日常服务领域和近 100 个虚拟工具。数据集包含英韩双语子集（英文 219 个会话、317 个规划案例、706 个工具调用实例；韩文 222 个会话、324 个规划案例、730 个工具调用实例），并覆盖约束验证与动态修订场景。人工标注确保了真实场景下的约束复杂性和对话自然度，避免了合成数据中常见的模板化偏差。

### 层级化 LLM-to-LLM 编排范式

OrchestrationBench 引入了**层级化“LLM-to-LLM”编排挑战**：主 LLM 作为编排器，基于自然语言能力描述动态协调专业化子 LLM，子 LLM 在工具调用前需执行预验证，并在约束未满足时发出 `TOOL CONSTRAINT VIOLATION` 信号。这一范式模拟了真实服务环境中多智能体协作的复杂性，为评估 LLM 作为“智能体管理者”的能力提供了标准化测试平台。

OrchestrationBench 将 LLM 驱动的智能体编排任务解耦为两个可独立评估的阶段：**工作流规划（Workflow Planning）** 与 **工具执行（Tool Execution）**。这一设计直接回应了现有评测基准的核心瓶颈——无法区分规划能力与执行能力，导致对模型编排行为的诊断粒度不足。

### 评测流水线

整个评测流水线采用 **逐步隔离评估（stepwise evaluation）** 策略，将用户请求的处理过程分解为以下关键模块：

1. **主 LLM 工作流规划器（Main LLM Workflow Planner）**：当且仅当接收到用户输入时，主 LLM 将用户请求分解为有向无环图（DAG）形式的工作流。每个工作流编码了任务依赖关系、执行状态及子 LLM 指派。独立请求或需中间确认的任务被拆分为独立工作流，而服务于同一连贯目标的多个步骤则被合并为统一工作流。

2. **子 LLM 工具执行器（Sub-LLM Tool Executor）**：每个子 LLM 根据主 LLM 的指派执行带约束验证的函数调用。执行前需完成约束检查，当约束不满足时发出 `TOOL CONSTRAINT VIOLATION` 信号；当需要用户补充信息时发出 `AWAIT FOR USER INPUT` 信号，两者共同构成拒识（rejection）决策。

3. **评估指标引擎（Evaluation Metrics Engine）**：从两个维度独立量化模型表现：
   - **规划评估**：基于图编辑距离（Graph Edit Distance, GED）计算工作流结构相似度，归一化至 [0,1] 区间后报告 1-GED 作为规划得分。工作流评分中，选择错误权重为 0.8，状态错误权重为 0.2。
   - **工具执行评估**：进一步分解为呼叫/拒识分类准确率与函数调用 F1 分数（含工具选择 F1、参数键 F1、参数值 F1）。

4. **LLM 裁判团（LLM Judge Ensemble）**：对函数调用参数的语义正确性进行三阶段验证——精确匹配、类型/模式校验、语义验证——并集成三个 LLM 裁判（GPT-4.1、Claude Sonnet 4、Gemini 2.5 Flash）的分数取均值。裁判团与人工标注的一致性达到中等水平（Cohen’s Kappa = 0.63）。

### 数据构建流程

数据集构建遵循五阶段人工标注流水线（Table 3），确保高质量与可控性：

| 阶段 | 内容 |
|------|------|
| **领域选择** | 覆盖 17 个日常服务领域（餐饮、旅行、金融等） |
| **虚拟工具设计** | 由 GPT-4o 生成、标注员精炼的近 100 个工具，配备适配 Agent-to-Agent 通信的智能体卡片 |
| **场景构建** | 设计多样化对话场景，包含约束验证与动态修订需求 |
| **多轮验证** | 标注员交叉校验工作流正确性与工具调用一致性 |
| **双语适配** | 同步构建英文与韩文子集，考虑文化差异调整场景细节 |

英文子集包含 219 个对话会话、317 个规划案例、706 个工具调用实例；韩文子集包含 222 个会话、324 个规划案例、730 个工具调用实例。多数会话涉及 2–3 个工作流与 2–3 个领域，调用结构以顺序与并行为主。

### 输入输出流

- **输入**：自然语言用户请求（英文或韩文），可能包含多轮交互与动态约束。
- **中间表示**：主 LLM 输出的结构化 DAG 工作流，包含步骤级规划、依赖关系与执行状态。
- **输出**：子 LLM 的工具调用决策（含选择、参数提取、约束验证结果）及最终聚合结果。
- **评估输出**：规划得分（1-GED）、呼叫/拒识分类准确率、函数调用 F1 分数及加权总分。

该框架的核心洞察在于：通过将规划与执行分离评估，揭示了工具执行性能在不同模型间相对一致，而规划能力差异巨大——例如 EXAONE-4.0-32B 的规划得分仅为 0.057，与最佳模型差距达 0.793，凸显了结构化规划评估的迫切需求。

## 核心模块与公式推导

OrchestrationBench 将 LLM 驱动的智能体编排分解为两个解耦的核心模块：**主 LLM 工作流规划器**与**子 LLM 工具执行器**，并通过独立的评估引擎对两者分别度量。这种解耦设计是该基准的核心创新——它使得规划能力与工具执行能力的评估相互独立，从而能够精确诊断模型在“思考”（规划）与“行动”（执行）两阶段的表现差异。

### 主 LLM 工作流规划器

该模块负责将用户的自然语言请求分解为结构化的有向无环图工作流。工作流模式明确定义了每个任务的执行状态、依赖关系及步骤级规划。具体而言：

- **工作流拆分与合并规则**：独立请求或需中间确认的任务被拆分为独立工作流；而服务于同一连贯目标的任务则合并为统一工作流。
- **触发机制**：主 LLM 的工作流生成**仅由用户输入触发**，确保评估的边界清晰可控。

### 子 LLM 工具执行器

该模块执行带约束验证的函数调用，包含两个关键子环节：

- **呼叫/拒识决策**：在调用工具前，模型执行预执行验证，当约束不满足时发出 `TOOL CONSTRAINT VIOLATION` 信号；`AWAIT FOR USER INPUT` 与 `TOOL CONSTRAINT VIOLATION` 共同构成拒识情形。
- **函数调用执行**：涵盖工具选择、参数键提取与参数值填充三个维度，均需通过领域特定约束的验证。

### 评估指标引擎

评估采用分步方式，将规划与工具执行完全隔离。核心指标如下：

**规划评估**：采用图编辑距离衡量生成工作流与参考工作流之间的差异，归一化到 $[0, 1]$ 区间后报告 $1 - \text{GED}$。工作流得分由结构得分与组件得分加权合成，其中**选择错误权重为 0.8**，**状态错误权重为 0.2**——这一权重分配反映了任务选择错误比状态标记错误对工作流正确性的影响更为严重的设计考量。

**工具执行评估**：进一步分解为两个序贯指标：
- **呼叫/拒识分类准确率**：衡量正确决策的比例。
- **函数调用 F1**：分别计算工具选择 F1、参数键 F1 与参数值 F1。

**语义裁判**：对于函数调用参数的语义正确性，采用三阶段验证流程（精确匹配 → 类型/模式校验 → 语义验证），并集成三个 LLM 裁判的分数取均值。裁判间一致性达到 Cohen’s Kappa = 0.63，属于中等水平，提示裁判偏好可能引入一定偏差。

> **注意**：本文未提供图编辑距离的具体计算公式，上述权重值（0.8 / 0.2）直接引自论文原文，其选取依据未经验证性实验支持，属于设计选择而非推导结果。

## 实验与分析

### 主结果：规划与工具执行能力的结构性分化

OrchestrationBench在英韩双语数据集上对17个主流LLM进行了系统评测，结果揭示了**规划能力与工具执行能力之间的显著结构性分化**。

**英文数据集总体表现**：Claude-sonnet-4与开源模型Qwen3-235B-A22B以0.842的总分并列第一，展示了开源模型在复杂编排任务上的竞争力。Gemini-2.5-pro-preview-06-05以0.839紧随其后。表现最差的模型为EXAONE-4.0-32B，总分仅0.415，与最佳模型差距达0.427（Figure 2）。

- **规划得分与函数调用得分的强相关**（英文数据集Pearson相关系数0.9215）：表明擅长工作流规划的模型通常也具备较强的工具调用能力，但这一相关性可能部分源于模型整体能力的共变，而非因果关联。
- **呼叫/拒识分类与规划得分的弱相关**（英文数据集仅0.5830）：说明判断是否需要调用工具这一决策能力与结构化规划能力相对独立，模型可能擅长规划但在边界决策上表现平庸，反之亦然。
- **跨语言一致性**：韩文数据集的相关性模式与英文基本一致，表明这些能力结构具有跨语言的稳定性。

### 模型能力画像的分化

不同模型家族在编排任务上展现出差异化的能力画像：

- **Gemini系列**（以Gemini-2.5-pro-preview为代表）在规划维度表现突出（英文规划得分0.850，韩文0.828），但函数调用能力相对较弱，呈现“强规划-弱执行”的特征。
- **Claude-sonnet-4**在函数调用上表现最强（英文0.885，韩文0.908），规划能力居中，呈现“强执行-中规划”的特征。
- **开源模型Qwen3-235B-A22B**在英文数据集上实现规划与执行的均衡，总分与Claude持平，但其韩文表现（0.804）与英文（0.842）存在明显落差，提示跨语言泛化仍有提升空间。
- **EXAONE-4.0-32B**在所有维度均表现最弱，尤其在规划任务上几乎完全失效（规划得分仅0.057），表明该模型在结构化工作流生成上存在根本性缺陷。

### 评测中的失败模式

通过对低分案例的分析，可归纳出以下典型失败模式：

1. **工作流结构错误**：模型生成的DAG与参考工作流在节点选择和依赖关系上存在重大偏差。由于图编辑距离中对选择错误赋予0.8的高权重，此类错误对规划得分的惩罚极为严重。EXAONE-4.0-32B的结构得分仅0.013（英文，Table 8a），表明其几乎无法正确识别所需的工作流步骤。

2. **约束感知失败**：在工具执行阶段，模型未能正确识别约束违反场景，错误地执行了本应拒识的调用。呼叫/拒识分类中“拒识F1”普遍低于“呼叫F1”（Table 9a），说明模型在识别不可执行请求方面存在系统性困难。

3. **参数提取偏差**：函数调用评估中，参数值F1通常低于键F1和函数名F1（Table 10a），表明模型在选择正确工具和参数键后，对参数值的精确提取仍存在挑战，这可能与领域特定约束的语义理解不足有关。

### 评测公平性说明

需注意以下可能影响结果解读的因素：

- **语义裁判的一致性限制**：函数调用参数的语义正确性由三个LLM裁判（GPT-4.1、Claude Sonnet 4、Gemini 2.5 Flash）集成评分确定，裁判间Cohen's Kappa仅为0.63（中等一致性），裁判模型自身的偏好可能引入系统性偏差。
- **图编辑距离权重未经验证**：工作流选择错误（0.8）与状态错误（0.2）的权重分配基于专家判断，缺乏系统的敏感性分析验证，可能影响规划评估的精确性。
- **领域覆盖的局限**：当前17个领域以消费服务场景为主，对医疗、法律、金融等高约束企业级场景的泛化性有限，且部分工具分布不均衡，长尾场景的评估代表性不足。
## 方法谱系与知识库定位

### 1 评测基准的定位与差异化

OrchestrationBench 的核心贡献在于将 LLM 驱动的智能体编排能力系统性地分解为**工作流规划**与**约束感知工具执行**两个可独立评估的维度。这一设计直接回应了现有评测基准的结构性缺陷：如 Table 1 所示，此前的基准（如 BFCL、τ-bench、ToolBench 等）在多智能体协作、函数调用、工具调用、多轮对话、规划评估及多语言支持等六个维度上均存在至少一项缺失，而 OrchestrationBench 是首个同时覆盖全部六个维度的基准。

该基准引入了一种层次化的“LLM-to-LLM”编排范式：主 LLM 作为编排器，根据自然语言能力描述动态协调多个子 LLM，将用户请求分解为有向无环图（DAG）形式的工作流（Figure 1）。这一架构与传统的单一 Agent 工具调用评测形成了明确的方法论区分。

### 2 方法适用边界

**适用场景**：
- 多领域、多步骤的服务编排任务，涵盖旅行预订、日程管理、购物推荐等 17 个日常消费服务领域（Table 6）。
- 需要约束验证与动态修订的交互场景，例如在工具调用前进行前置约束检查，或在用户确认后才执行关键操作。
- 双语（英语、韩语）环境下的智能体能力评估，数据集考虑了文化差异对场景设计的影响。

**不适用或需谨慎推广的场景**：
- 当前数据集以消费服务领域为主，对企业级复杂业务流程（如供应链管理、合规审查等）的泛化性有限。
- 工具集规模约 100 个，且部分领域工具分布不均衡，对长尾服务场景的覆盖不足。
- 评估采用 turn-by-turn 方式，未度量端到端工作流中的错误传播效应，因此无法直接反映真实部署中的级联失败风险。

### 3 局限性与开放问题

**已知局限**：
1. **GED 权重未经验证**：工作流评分中，选择错误权重（0.8）与状态错误权重（0.2）的设定缺乏消融实验或敏感性分析支持，可能影响评估的准确性。
2. **语义裁判一致性有限**：LLM 裁判团（GPT-4.1、Claude Sonnet 4、Gemini 2.5 Flash）与人工标注的一致性仅为中等水平（Cohen’s Kappa = 0.63），裁判自身的偏好可能引入系统性偏差。
3. **数据集规模与覆盖**：英韩双语子集各包含约 220 个会话、320 个规划案例和 700 余个工具调用实例（Table 7），对于训练或 fine-tuning 而言规模偏小；且多数会话仅涉及 2-3 个领域和工作流（Figure 6），复杂跨域编排的评估密度不足。

**核心开放问题**：
- **规划-执行差距的成因与弥合**：实验揭示的核心发现是工具执行性能在不同模型间相对一致，而规划能力差异巨大（EXAONE-4.0-32B 的规划得分仅 0.057，而最佳模型达 0.850）。这一差距的深层原因——是训练数据的规划信号不足，还是架构层面的推理能力差异——尚待探究。
- **端到端错误传播建模**：当前 turn-by-turn 评估无法捕捉规划错误如何向下游工具执行传播并放大。如何设计端到端评估协议，量化错误传播对整体任务成功率的影响，是一个重要的方法学问题。
- **训练策略设计**：基于评测发现，如何设计针对性的训练策略（如规划专用的强化学习奖励设计、规划-执行联合优化）以同时提升两项能力，是后续工作的关键方向。

### 4 知识库定位

OrchestrationBench 处于 **LLM Agent 评测**与**工具增强语言模型**两个研究方向的交叉点。其方法论贡献不在于提出新的模型架构或训练算法，而在于建立了一套结构化的评估框架，将编排能力从“黑箱端到端评测”推进到“分阶段、可归因的组件级诊断”。这一框架为后续的 Agent 训练研究提供了明确的优化目标分解：规划能力应作为独立于工具调用能力的优化维度。
